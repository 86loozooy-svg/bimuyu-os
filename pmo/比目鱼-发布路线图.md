# 比目鱼（Studio OS）· 发布路线图

> **版本**：v1 ｜ **确立**：2026-08-12 ｜ **周期**：3 个月快速验证（目标 ~2026-11-12 前上线售卖）
> **性质**：战略时间线层，位于 PMO 宪法 / PLAN.md 之上。
> **约束继承**：宪法与 PLAN.md 的全部规则（P0/P1/P2、任务卡 `本地/服务器/设计` 标签、视觉冻结 OS4.01、C 模式官方自营）在本路线图中 **继续生效**，冲突时以宪法为准。
> **产品定位**：中文名「比目鱼」，域名 `bimuyu.work`，商业模式 **SaaS 订阅制**，设计基本完成、进入落地期。

---

## 0. 战略定锚（为什么是「3 个月快速验证」）

- 目标不是"做完美产品"，而是"用最小成本验证比目鱼**能否卖出去**"。
- 阶段之间设 **决策门（Gate）**：每过一道门必须停一下、确认后再进下一阶段，防止跑偏、防止"做了半天发现方向不对"。
- **验证成功硬指标（初版假设，待 Jerry 在定锚周确认数值）**：
  - 公开上线后 **30 天内** ≥ \_\_ 个注册
  - 同期 ≥ \_\_ 个付费订阅
  - 首月 MRR ≥ ¥\_\_
- **未达标处置**：转入下一轮迭代，不硬上；已验证的部分沉淀为资产。

## 1. 五阶段总览（13 周）

| 阶段 | 周次 | 主题 | 核心交付 | 决策门 |
|---|---|---|---|---|
| **P0 定锚** | 第 0 周 | 锁目标 / 锁模型 | 路线图冻结、套餐骨架、验证指标 | → 进入 Build |
| **P1 技术落地 MVP** | 第 1–4 周 | 设计稿变可运行产品 | 最小可用功能集 + 多租户账号 | G1：达内测标准？ |
| **P2 商业化模块** | 第 5–7 周 | 能收钱 | 订阅/支付/计费后台 + 落地页 | G2：能邀种子？ |
| **P3 内测与种子** | 第 8–10 周 | 验证付费意愿 | 邀请制内测 + 反馈迭代 + 宣发素材 | G3：达公开标准？ |
| **P4 发布与售卖** | 第 11–13 周 | 上线卖 | 正式上线 + 宣发 + 运营看板 | → 转运营期 |

> **节奏提示**：P1 技术周最紧（依赖设计稿实现度）；P2/P3 的宣发素材可提前并行准备；任何阶段若卡住，先回退到上一道决策门重判，不盲目硬推。

## 2. 各阶段详细清单

### P0 · 定锚周（第 0 周）
- [ ] 冻结本路线图 v1，写入 PMO（本文件）
- [ ] 宪法补充「比目鱼」品牌条款：中文名、域名 `bimuyu.work`、SaaS 订阅定位
- [ ] 收敛 SaaS 套餐骨架（初版假设，数字待定）：
  - 免费试用 14 天 / 入门版 ¥\_\_/月 / 专业版 ¥\_\_/月 / 团队版 ¥\_\_/月
- [ ] 敲定「验证成功硬指标」具体数值（见 §0）
- [ ] 列出本期 **Open Decisions（待决策清单）** 并指派责任人/时限（见 §4）
- [ ] 确认设计稿已 100% 冻结（OS4.01 为事实来源，无遗留改动）

### P1 · 技术落地 MVP（第 1–4 周）
- [ ] 把已定设计稿实现为可运行产品（本地优先，复用 8013 + 自检技能）
- [ ] 切出 **最小功能集**：只做验证商业假设所必需的功能，不做锦上添花
- [ ] 账号/多租户体系：注册 / 登录 / 租户隔离（SaaS 必需，现有 `collaborators` 表可扩展）
- [ ] 任务卡按 PMO 规则拆解（每条标 `本地/服务器/设计`），功能上线前必有卡 + 自检结论
- [ ] 沿用每周日自动化备份 + 8013 自检
- **G1 决策门（第 4 周末）**：MVP 是否达到内测标准？→ 否则回到 P1 收尾，不进 P2

### P2 · 商业化模块（第 5–7 周）
- [ ] 订阅/计费：套餐、支付对接（渠道见 Open Decisions）、用量/配额
- [ ] 计费后台：订阅状态、发票、升降级、取消/退订
- [ ] 落地页 + 定价页（承载在 `bimuyu.work`）
- [ ] 品牌站最小版（可先用落地页代替完整官网，见 Open Decisions）
- [ ] 隐私政策 / 服务协议（SaaS 收款合规最低要求）
- **G2 决策门（第 7 周末）**：能否开始邀请种子用户？→ 支付/合规未就绪则延期，不裸奔上线

### P3 · 内测与种子用户（第 8–10 周）
- [ ] 邀请制内测（**C 模式**：官方自营，不开放公开注册轰炸，宪法·全局约束 5）
- [ ] 反馈收集 → 快速迭代（仍遵守视觉冻结 / 任务卡规则）
- [ ] 定价假设验证：种子用户真实付费意愿
- [ ] 宣发素材积累：产品截图、演示短视频、首篇案例/故事
- **G3 决策门（第 10 周末）**：是否达到公开上线标准？→ 指标/稳定性不达标则延长内测

### P4 · 发布与售卖（第 11–13 周）
- [ ] 正式上线 `bimuyu.work`
- [ ] 宣发启动：发布文案、设计/工作室圈层触达、社媒分发
- [ ] 首批付费转化 + 客服承接（退款/答疑 SOP）
- [ ] 上线后第 1 周运营看板：注册 / 转化率 / 留存 / MRR
- [ ] 宪法更新「比目鱼已发布」里程碑；本路线图转入 **运营期版本**

## 3. 防失忆机制（这是 Jerry 最担心的部分）

周期一长，分散在多轮对话里的决策最易被冲淡。用三层锚点锁死：

1. **本路线图 = 唯一时间线脊柱**。每完成一个阶段/勾选一项，就地更新，不另起文件。
2. **ACTIVITY.md 动态日志 = 里程碑救命线**。每过一道决策门（G1/G2/G3）或完成重大里程碑，写一条：
   `[日期] [决策门] G1 通过，MVP 达内测标准` / `[日期] [里程碑] 比目鱼正式上线`
3. **定期状态同步**。随时对我说"跑一次状态同步"，我据本文件 + ACTIVITY.md 汇总当前进度、卡点、待决策项，帮你把散掉的思绪重新对齐。

> 习惯建议：每个决策门当天，顺手让我记一条动态。半年后回看，这就是比目鱼从 0 到上线的完整脉络。
